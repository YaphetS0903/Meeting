# 企业微信待办长期接入方案核查

用户已选择同时接入自建应用原生待办与应用消息。双通道已部署；真实客户端创建待办仍待使用人确认验收。

## 发现的官方替代路线

官方自建应用具有原生待办的客户端创建、查看接口，以及服务端读取、更新状态接口。它使用自建应用身份，与目前 CLI 机器人的能力授权不同。

- [创建待办 createTodo](https://developer.work.weixin.qq.com/document/path/101530)：在企业微信客户端内调起原生创建页，预填 `content`、`attendees`、`endTime`，成功回调返回 `todoId`。仅打开面板，必须由用户确认，不支持纯服务端静默创建。截止时间可不填。需要注册应用身份、自建应用全员可见、当前成员在可见范围，客户端至少 5.0.9。
- [查看原生详情 viewTodo](https://developer.work.weixin.qq.com/document/path/101531)：只打开本应用通过 createTodo 创建的待办详情，不返回业务数据。
- [服务端获取待办](https://developer.work.weixin.qq.com/document/path/101524)：`POST /cgi-bin/todo/get`，使用自建应用 access_token，读取内容、创建人、整体状态、参与人状态、截止时间及提醒。
- [服务端更新待办状态](https://developer.work.weixin.qq.com/document/path/101534)：`POST /cgi-bin/todo/update`，只能修改本应用创建的待办，应用可见范围须包含根部门。参数支持整体 `status`（0 完成、1 进行中）与最多 20 人的 `attendees` 及状态；未提供修改标题、截止时间或删除的参数。
- [自建应用凭证](https://developer.work.weixin.qq.com/document/path/91039)：应用 Secret 获取 access_token，通常两小时有效，由服务端缓存和重新获取，不需要每周机器人续授权。

以上页面已直接从官方开发者中心读取；网页搜索工具无法渲染页面，使用只读 HTTP 获取并提取正文核对，未调用任何生产待办写接口。

## 现有应用只读预检

生产“会议纪要任务单”自建应用已启用、可见范围包含根部门、已配置可信域名。具备接入的主要基础条件，仍需新增 JS-SDK 注册和签名服务、前端创建流程、可信关联校验及实际客户端验收。

## 两种可选方案

1. **自建应用接原生待办。** 派发人在企业微信中填写系统任务，再在预填的原生面板确认创建；保存 `todoId` 并关联系统任务，验证通过后由服务器完成原生待办。没有机器人的每周续授权问题。限制是创建必须人工确认，内容及截止日期不能通过上述服务端接口自动更新；周期实例也无法无人值守创建原生待办。
2. **应用通知卡片加系统任务列表。** 通过现有自建应用发送任务通知，点击进入系统“我的任务”，到期及验证通知自动发送。服务器能够持续运行，完整任务状态由本系统控制；消息不进入企业微信原生待办列表。只对直接派发启用时，需要新增消息来源控制，不能直接打开现有全局提醒开关，否则会议消息与邮件也会受到影响。

保留原生待办且接受每次派发一次确认时，方案一更贴近原要求；要求完全自动创建、改期与周期派发时，方案二更适合。

## 接入前需处理

- 当前 CLI 待办属于“王晨宁的机器人”，自建应用不能更新它们。需记录提供方，按原通道收尾已存在待办，避免重复创建。
- 先校验 JS 创建返回的待办真实来源、内容、责任人与系统派发权限，再保存映射。取消原生创建、网络中断及重复回调必须能够恢复，不能制造重复任务或假定成功。
- JS 注册需使用页面实际 URL 签名，并保持服务器可信 IP、可信域名及可见范围有效；具体实现仍待选定方案后进行。
- 若采用消息方案，原生待办和消息分别控制，会议和邮件继续关闭；现有被跳过的历史消息不能直接批量补发。

桌面自动续授权的[社区工具](https://github.com/fyaic/wecom-auth-keeper)仍为实验性方案，依赖常驻且已登录、可操作的 Mac。作者报告的预续期实测包括文档与通讯录，未完整覆盖待办、完整导航及跨周期运行，不能作为已验证的生产解决方案。

## 已实现的双通道

- 新直接派发任务保存成功后独立入队发送应用消息卡片，附任务、派发人、截止日期和详情链接；任务调整、完成申请、验证结果、撤回、到期与待验证汇总使用同一来源控制。入队、实际发送与管理员重试都会重新核查来源；混合汇总逐项过滤，会议任务与邮件开关保持关闭。
- `WECOM_DIRECT_NOTIFICATIONS_ENABLED=true` 独立开启直接任务消息；原全局 `reminders.enabled=false` 控制会议提醒及纪要邮件。保存关闭状态不会取消已允许的直接任务消息。历史被跳过的通知不补发。
- `NATIVE_TODO_APP_ENABLED=true` 与原生总开关及直接来源开关配合，新直接任务停止机器人自动创建。派发人在企微内使用本人绑定账号派发成功后，立即自动打开预填的原生确认窗，确认后责任人直接收到待办。普通浏览器派发时，绑定企微的派发人收到确认卡片，打开后自动弹窗；卡片延迟一分钟发送，已创建待办则跳过。未绑定企微的管理员账号使用责任人应用消息。实际派发人可重新确认，责任人及其他管理员不具备创建入口。保持预填内容、人员、日期后确认。日期可留空；原生同步最多20位责任人，更多人员仍使用应用消息。SDK 使用官方 `@wecom/jssdk 2.4.4`，先探测客户端支持；最低客户端要求5.0.9。
- 注册使用原业务应用的企业与应用双签名，服务器缓存两类 ticket 并串行刷新；签名只允许当前 PUBLIC_URL 域名和协议。token 到期自动重新获取，不需要每周机器人授权。生产应用全员可见、可信域名及两类 ticket 已只读预检通过。
- 创建前保存唯一尝试，按任务锁串行防止重复点击及多标签页并发；取消释放尝试。回调先在当前标签页保存待办编号，再提交服务器。关联校验真实创建人、内容、参与人、截止时间与创建时间，并通过更新接口校验归属本应用；重复回调返回既有关联。响应丢失可恢复关联，结果未知不自动再创建；若回调编号完全丢失，需人工核实待办后处理。
- 映射新增 `provider=app/cli`，旧数据默认cli；旧机器人待办保留原通道收尾。自建应用新待办不依赖机器人授权。系统验证关闭或撤回后完成原生待办；原生客户端自行完成不绕过系统验证。人员调整同步参与人，保留现有参与人状态；内容与日期无法由服务器修改，详情明确显示差异并以系统安排为准。
- 数据库为增量迁移 `20261013_app_native_todo`，新增原生创建尝试表和提供方／原始安排字段。
