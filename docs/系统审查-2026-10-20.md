## 1. 自动保存可能把接续会议草稿写入上一场会议（P1）

位置：[Meeting.vue:338](/Users/chenny/workspace/codex/会议纪要任务单系统/frontend/src/pages/Meeting.vue:338)，后续自动保存安排在第 371 行；路由参数变化处理在第 300 行。

触发过程：会议 A 已发布并进入修订 → 修改内容触发自动保存 → 保存响应尚未返回时点击“接续新建”进入 B → B 加载完成后，A 的保存响应才返回。

`save()` 无条件把当前 `meeting` 写回 A，而 `draft` 此时已经是 B；比较后又判定为未保存并重排定时器。下一次请求携带 A 的最新版本号，把 B 草稿提交到 A，后端版本校验无法拦截。

隔离复现记录的两次请求分别为：`PUT /meetings/A` 携带 A 草稿、`PUT /meetings/A` 携带 B 草稿。影响首先发生在修订草稿，已发布快照不会立即被修改。

已排除的保护：`App.vue:297` 的 RouterView 没有 key；两页使用同一个 `/meetings/:id` 路由组件；组件只有离开守卫，没有参数更新守卫；接续按钮允许保存中操作，后端也允许修订中接续。

建议将加载、保存响应和定时器绑定会议 ID 与页面世代；同组件切换会议时处理在途保存和未保存修改。

## 2. 修订会议归属后，已有任务仍留在旧部门/系列（P1）

位置：[business.py:759](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/business.py:759)；任务部门访问规则见 [access.py:148](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/access.py:148)。

触发过程：发布部门 A、系列 A 的会议及任务 → 修订为部门 B、系列 B → 发布。发布代码更新了 Meeting，但已有 Task 的 `department_id` 与 `series_id` 没有同步。

隔离复现结果：旧部门普通同事已经不能查看会议，却仍能查看该任务；新部门普通同事能看会议却看不到任务；从新系列带入任务得到 0 条。这同时影响权限和归档一致性。

建议统一修订发布与归档调整的处理规则，更新本会议来源任务的当前归属，保留历史版本快照；对旧部门、新部门的普通成员分别核对权限。

## 3. AI 分析会覆盖用户手工更正的历史状态（P2）

位置：[Validation.vue:209](/Users/chenny/workspace/codex/会议纪要任务单系统/frontend/src/pages/Validation.vue:209)，异步批量应用在第 244 行。

触发过程：打开有状态识别问题的历史会议，自动 AI 分析开始 → 等待期间手工改成“已完成” → AI 随后建议“未完成”。代码只检查原始问题标记，没有检查字段是否已被人工更改，直接覆盖为“未完成”。如果继续确认入库，错误状态会进入考核。

隔离复现输出：人工设置“已完成”，AI 返回后变成“未完成”。同一请求在退出审核页面后返回，还会因为 `payload` 已置空而报 `Cannot read properties of null (reading 'items')`。

建议请求绑定候选 ID、页面世代和请求时字段值，只应用用户尚未修改的字段；离开页面后忽略旧响应。

## 4. 接续新建遗漏尚未回顾的已完成任务（P2）

位置：[business.py:981](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/business.py:981)。

触发过程：上周任务发布 → 责任人申请完成 → 验证通过 → 接续新建本周会议。接续逻辑直接跳过所有 `closed_at` 非空任务，未区分是否已经完成会议回顾。

隔离复现：接续新建产生 0 条回顾；相同状态调用“带入上期任务”则得到 1 条“已完成”。这会漏掉首次完成回顾，进而漏计已完成人次。

建议统一使用现有带入规则，区分“任务已验证关闭”与“关闭结果已在会议回顾中统计”。

## 7. 修改任务会使待发送的派发确认卡片失效（P2）

位置：[business.py:534](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/business.py:534)；旧版本跳过规则见 [integrations.py:419](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/integrations.py:419)。

触发过程：在浏览器直接派发任务 → 60 秒延迟确认卡片尚未发送 → 修改日期、说明或责任人。任务版本升级，原确认事件仍携带旧版本，发送时被跳过；修改逻辑仅通知责任人，没有安排新的派发人确认卡片。

隔离复现：任务 version=2、确认事件 version=1，发送结果为 skipped“任务已更新或关闭”。派发人因此收不到约定的确认入口。

建议更新未发送事件或创建按版本区分的新事件。现有确认事件键固定为 `task:{id}:native-confirm`，只重复调用现有排队函数不足以解决去重问题。

## 8. 周期直接任务缺少派发人确认流程（P2）

位置：[recurrence.py:266](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/recurrence.py:266)；应用待办模式提前返回位置为 [business.py:116](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/business.py:116)。

自动生成下一期直接任务时，只安排责任人应用消息，再调用原生待办排队函数。当前应用模式遇到没有映射的新任务直接返回，周期生成逻辑没有补充派发人确认卡片。

隔离复现：新周期任务只有一条责任人消息，没有原生待办事件，也没有派发人确认卡片。生产当前没有周期规则，属于启用后会遇到的缺陷。

建议复用普通直接派发的确认流程，在生成周期任务后向实际派发人排确认卡片，仍由派发人在企微确认创建。

## 9. 中文企微应用卡片超出描述字节上限（P2）

位置：[integrations.py:493](/Users/chenny/workspace/codex/会议纪要任务单系统/backend/app/services/integrations.py:493)。

文本卡片 description 限制是 512 字节，代码使用 Python 字符串长度计算预算。中文、HTML 转义和省略号都可能使实际 UTF-8 字节数明显超标。

替代企微接口捕获的示例为 486 字符、1384 字节；按 512 字节截断后，末尾截止日期、派发人字段均消失。没有向真实员工发送该示例，实际客户端显示仍需修复后验收。

建议按转义后的 UTF-8 字节预算截断正文，预留完整页脚与省略号。接口限制参考：[发送应用消息文档](https://s.apifox.cn/apidoc/docs-site/406014/api-10061358)。这是应用消息卡片的问题，与已确认的原生待办独立 description 字段限制不同。
