# 运行监控与通知失败告警

monitor 是独立进程，每 60 秒检查一次。数据库、Redis、worker 或 beat 故障不会让它随后台调度一同停止。数据库连接、查询及网络请求有独立超时；检查失败以异常项展示，不以没有记录认定正常。

## 检查范围

| 检查项 | 默认触发条件 |
|---|---|
| 数据库 / Redis | 无法连接或读取 |
| 调度执行心跳 | dispatch 最近 180 秒没有开始执行；无心跳也报警 |
| 通知明确失败、配置阻塞、送达不明 | failed、blocked、uncertain 任一数量大于零 |
| 后台积压 | pending 已到执行时间超过 15 分钟；未来计划时间不算积压 |
| 执行中断 | sending 已开始超过 10 分钟 |
| 通讯录 | 最近一次同步失败，后续成功会解除 |
| 附件目录 | 不可读写或可用空间不足 512 MB |
| 备份 | 48 小时内没有同时包含数据库转储、附件归档和清单的备份 |

备份监控只核对完整文件集合与时间，不在每次轮询重新读取全部附件；必须继续执行哈希校验和恢复演练。磁盘检查只针对附件目录所在文件系统，数据库卷容量及整机状态需企业基础设施监控。

## 配置告警接收端

告警可以选择 Webhook 或邮件。使用 Webhook 时，在私有 `.env` 设置 `ALERT_WEBHOOK_URL` 和可选 `ALERT_WEBHOOK_TOKEN`；生产地址必须为 HTTPS，不跟随重定向，本地测试允许回环地址 HTTP。使用邮件时设置 `ALERT_EMAIL_TO`，系统沿用已经配置的 `SMTP_*` 参数发送故障和恢复邮件。两者同时配置时优先使用 Webhook。

告警邮件使用稳定事件编号生成 `Message-ID`，同一事件重试保持编号不变。邮件只包含检查项、汇总结果、时间和系统管理地址，不包含会议内容、人员任务或凭据。告警收件人与业务成员提醒相互独立，成员提醒总开关关闭时仍会发送运维告警。

Webhook 是企业告警系统提供的 JSON POST 接收接口，**不是企业微信群机器人的现成消息格式**。若使用群机器人或值班平台，应在企业接收端把本系统事件转换成目标格式。无需启用原生企业微信待办。

每次请求包含：

- `event_id`：该次告警的稳定编号，同时作为 `Idempotency-Key` 请求头。
- `type`：`incident` 异常或 `recovery` 恢复。
- `service`、`occurred_at`、`checked_at`、`management_url`。
- `issues`：异常代码、中文名称、结果和汇总说明。
- `queue_counts`：各发送状态数量。

配置 token 时发送 `Authorization: Bearer ...`。接收端返回 2xx 表示已可靠接收；其他状态或超时按未确认处理。请求不包含任务正文、员工姓名、会议内容、数据库连接字符串、SMTP 密码或企业微信密钥。

异常类别变化时立即发送；相同类别持续存在默认每 60 分钟提醒一次。只有备份过期这一项异常时，每 24 小时提醒一次；其他异常仍按 60 分钟提醒。恢复时发送恢复事件。失败在后续检查重试，相同事件保持同一个编号；**接收端必须按 event_id 去重**。网络超时可能发生“接收端已收到但确认响应丢失”，所以告警提供至少一次投递，不承诺外部恰好一次。业务任务消息仍保留原来的 uncertain 人工核实流程。

监控状态持久保存在独立 `monitor-state/` 目录，包含最近检查、确认发送时间和待重试事件编号，不保存接收 URL/token。进程持有文件锁，防止同一存储目录重复启动 monitor。后端读取超过三个检查周期的状态时显示监控已过期，不将旧的正常结果视为当前健康。

## 启动和验证

```bash
docker compose -f docker-compose.yml -f docker-compose.app.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.app.yml logs --tail=30 monitor
docker compose -f docker-compose.yml -f docker-compose.app.yml exec monitor python -m app.monitor --check
```

从另一台网络主机执行只读外部探测，确认入口、健康接口和企业微信校验文件都能到达。脚本不会登录、写入业务数据或发送通知：

```bash
BASE_URL=http://mail.trqcns.com:4023 bash scripts/external-healthcheck.sh
```

如果企业微信校验文件发生变化，可通过 `WECOM_VERIFY_PATH` 和 `WECOM_VERIFY_CONTENT` 传入新的路径及原文；不要把密钥放入命令行或脚本参数。

`--check` 只检查监控自身心跳，不发送测试消息。`--once` 会执行一次实际检查及符合规则的告警，存在异常时返回 2；运行中的 monitor 持有锁时，不可并行执行第二个检查发送进程。

系统管理中确认：监控正在运行、各检查项已更新、告警接收端及当前通道已显示。真实联调时先发送明确标注的通道测试，再在独立试运行环境制造可恢复的发送失败，核对接收端收到 incident；修复问题后核对 recovery；检查重复事件去重及重新启动后保持发送记录，再完成上线验收。不要用真实业务消息反复发送来模拟失败。

## 可调阈值

`.env.example` 提供 `MONITOR_INTERVAL_SECONDS`、`MONITOR_HEARTBEAT_SECONDS`、`MONITOR_QUEUE_MINUTES`、`MONITOR_FREE_MB`、`MONITOR_BACKUP_HOURS`、`ALERT_REMINDER_MINUTES` 和 `BACKUP_ALERT_REMINDER_MINUTES`。修改后重建相关容器使环境生效。

## 当前验收边界

自动化测试通过本机 HTTP 接收端验证 Webhook 请求体、鉴权、事件编号和确认机制，并验证邮件收件人、稳定 `Message-ID` 及正文边界；同时覆盖依赖服务故障、超时重试、恢复、过期备份及权限隔离。整台服务器宕机、监控目录不可写或告警渠道自身持续故障，需要部署环境之外的健康探测补充覆盖。
